(2) Why it is correct: the total is converted once to integer cents. Each person gets floor(cents / people), and the leftover `extra` cents (0 <= extra < people) go one each to the first `extra` people. So the shares sum to exactly the total in cents and differ by at most one cent. `Number.isInteger` rejects 0 (via `< 1`), -2, NaN, 2.5, '3' and undefined with a RangeError. It builds a new array and never touches its inputs, so AC4 holds, and splitEvenly(10, 2) still gives [5, 5].

By hand, 10/3 gives [3.34, 3.33, 3.33], and 0.01/3 gives [0.01, 0, 0], which sorts to [0, 0, 0.01] under the test's default `.sort()`. 222.55/3 gives 22255 cents as 7419, 7418, 7418, which sums to 22255. I did not run these.

(3) Risks and assumptions:
- The remainder is computed as `cents - base * people` rather than `cents % people`. This keeps it non-negative with `floor`, so negative amounts such as refunds still sum exactly. No test covers negative amounts.
- A non-finite or non-numeric `amount` (NaN, a string) is not validated and yields NaN shares. R1 and the tests only require validating the people count, so I left it out to keep the change minimal.
- The extra cent always goes to the earliest person, so shares are not in descending order for negative amounts. The tests do not check order.
- `Math.round(amount * 100)` can misround on floating-point half-cent inputs such as 1.005. That is the same assumption the existing `total()` makes.
- Very large `people` counts, such as 1e9, would build a huge array. Both the old and new code behave this way.
