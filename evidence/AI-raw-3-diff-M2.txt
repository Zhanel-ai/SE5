(2) Why it is correct: `validateExpenses` throws a `TypeError` for every case in `tests/validation.test.js`. Each message starts with "expenses must be a list" or "item N: ", where N is 1-based. `cli.js` now handles the missing argument with the usage line and exit 2. It also validates the parsed JSON and computes the split before printing anything. So a bad file, bad JSON, a missing file or an invalid people count (`splitEvenly` throws `RangeError` for NaN, 0 and 2.5) goes to the catch block. That prints one `Error: <message>` line to stderr and exits 2, with no partial stdout and no stack trace. The success output uses the same strings in the same order, so it should be byte-identical.

(3) Risks and assumptions:
- Unspecified message: I added "item N: must be an object" for null or non-object items. The test only requires the `item N: ` prefix.
- Whitespace categories: A category of only whitespace (for example " ") passes validation, because the spec says "non-empty string".
- Spec-compliant but odd inputs: An amount of 0 is accepted (>= 0). A people argument of "" falls back to 1 (existing `|| 1` behaviour), and "1e1" is accepted as 10.
- Error text: An ENOENT message includes the file path and system text on one line. Messages from non-Error throws are stringified.
- Exit paths: `process.exit(2)` is called right after `console.error`. Stderr is normally flushed for pipes and files, but I haven't run it to confirm.
- Out of scope: Category names like "constructor" or "__proto__" still behave oddly in `categoryTotals`. I left that alone under the no-unrelated-changes rule.
